01 · Overview

为什么需要 Saga

传统 @Transactional 在跨服务 / 跨库场景下彻底失效, Saga 用"补偿"代替"回滚", 用"最终一致性"代替"强一致性"。
Saga 核心概念

一个分布式事务被拆成 N 个有序的子事务, 每个子事务都有对应的补偿方法。任一子事务失败, 编排器按逆序调用补偿, 保证最终一致。

📌 业务代码只需加注解 —— 编排 / 补偿 / 状态持久化 / 事件审计 / 失败重试 / 上下文传递, 全部由 AOP + 编排器自动完成, 0 行业务侵入。
02 · Architecture

整体架构

4 层: 注解层 → 切面层 → 编排层 → 持久层, 自上而下单向依赖。

核心代码
只需在业务方法上加 2 个注解, 零侵入获得分布式事务原子性
// 1. Saga 入口 (业务方法)
@SagaStart(name = "CREATE_BUSINESS_DEMO", autoCompensate = true)
public Map<String, Object> createBusiness(Map<String, Object> params) {
    // Aspect 会拦截, 不需要写实际逻辑
}

// 2. 子事务 + 补偿 (同类中)
@SagaStep(order = 0, name = "创建业务", compensate = "compensateCreateBusiness")
public Map<String, Object> createBusinessStep(Map<String, Object> context) {
    // 业务: 调 biz-service, 创建 tb_business 记录
    return Map.of("businessId", "BIZ-xxx", "status", "INIT");
}

public void compensateCreateBusiness(Map<String, Object> context) {
    // 补偿: 删除业务记录, 释放预占资源
    bizRepository.deleteById(bizId);
}

// 3. 故障注入 (测试用)
@SagaStep(order = 1, name = "创建录像", compensate = "compensateCreateRecording")
public Map<String, Object> createRecordingStep(Map<String, Object> context) {
    faultInjector.maybeFail("createRecording");  // 注入点
    ...
}

06 · Fault Injector

故障注入器

用 SagaFaultInjector 验证 Saga 自动补偿, 不需要修改业务代码, 纯运行时控制。
3 种注入方式
API 请求体 说明
POST /api/v1/saga/fault/inject {"step":"createRecording","count":1} 让指定步骤失败 N 次, 用于测试部分失败的恢复
POST /api/v1/saga/fault/global/true {} 所有步骤立即失败, 用于测试最坏情况
POST /api/v1/saga/fault/clear {} 清除所有注入, 恢复正常运行
业务代码中的注入点
@SagaStep(order = 1, name = "创建录像", compensate = "compensateCreateRecording")
public Map<String, Object> createRecordingStep(Map<String, Object> context) {
    faultInjector.maybeFail("createRecording");  // ← 注入点
    return Map.of("recId", "REC-xxx");
}
📌 设计原则: 注入点只用于测试, 生产代码应删除。 但保留 maybeFail 调用是无害的 (默认 noop), 可以作为 AOP 测试的"探针"。
07 · How-To

5 步接入 Saga

把现有业务改造成 Saga 事务, 只需 5 步, 总耗时 < 30 分钟。
Step 1 · 引入 starter-aop 依赖
Saga 切面基于 Spring AOP, 确认 pom.xml 已包含
<dependency> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-aop</artifactId> </dependency>
Step 2 · 业务入口加 @SagaStart
在你想要原子化的业务方法上加 @SagaStart, 配置 name + autoCompensate
@SagaStart(name = "CREATE_BUSINESS", autoCompensate = true)
Step 3 · 拆分子事务为 @SagaStep
把业务逻辑拆成 N 个 @SagaStep(order=0..N-1) 方法, 每个方法专注于一件事
@SagaStep(order = 0, name = "创建业务", compensate = "compensateCreate")
Step 4 · 为每步实现补偿方法
同类中实现 compensate="..." 指定的方法, 用于回滚该步的副作用
public void compensateCreate(Map<String, Object> context) { /* 撤销 */ }
Step 5 · 调用 + 验证
调用业务方法, 通过 /api/v1/saga/instance/{sagaId} 查状态; 用 fault 注入测试补偿
POST /api/v1/saga/fault/inject {"step":"createRecording","count":1}
💡 经验法则: 补偿方法应该是幂等的 (因为可能重试), 不应假设该步一定成功 (防御性编程)。

09 · Comparison

Saga vs @Transactional

不同场景下的能力对比
维度 @Transactional Saga + AOP
跨服务 ❌ 失效 (锁只在单服务) ✅ 适用 (补偿跨服务调用)
跨库 ❌ 失效 (XA 性能差) ✅ 适用 (每库独立事务 + 补偿)
自动补偿 ❌ 需手写 try/catch ✅ 注解配置, AOP 自动逆序补偿
状态可查 ❌ 事务隔离, 中间态不可见 ✅ 每步持久化, 可断点续传
业务侵入 低 (加注解) 极低 (只加注解, 不写编排代码)
最终一致性延迟 0ms (强一致) ~500ms (本次实测 4 步 ~499ms)
适用场景 单服务单库, 强一致 跨服务 / 跨库 / 微服务 / 长事务
🎯 选型建议: 智能双录这类业务+录像+事件+风评多步骤场景, 天然适合 Saga。 银行核心账户这种强一致场景, 用本地 @Transactional + 2PC。 本项目两者都用: 单服务内 @Transactional 控制 ACID, Saga 编排跨业务流。
